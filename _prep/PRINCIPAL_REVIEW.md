## Pillar 1 — Django Backend (10 / 10)

### What lands

- **Schema is domain-first.** `Industry → Brand → Review + Reviewer` — four clean models. No `JSONField`
  postmeta blobs, no WP table shape preserved. The candidate made explicit field-mapping decisions and
  documented them.

- **Dual-path rating is both correct and auditable.** `migrated_average_rating` is stored for
  comparison; `computed_average_rating` from `with_stats()` is authoritative. The `__dict__` setter
  trick lets a queryset annotation "land" on an instance that also defines a property of the same name
  — a non-trivial Django descriptor detail that most engineers get wrong.

- **`ImportLedger` three-way branch is correctly implemented.** The "live row exists → upsert",
  "ledger has it → skip", "neither → create" logic maps cleanly to the source. This is the right
  idempotency primitive; `get_or_create` would silently resurrect rows the admin deleted.

- **`WordPressSource` Protocol** isolates `SqlDumpSource` from `MariaDbSource` behind an interface
  boundary. The streaming dump parser (`line-by-line`) keeps import memory flat regardless of dump
  size. That's the right call.

- **Indexes are present and targeted.** Migration `0002` adds `review_rating_idx` (scalar filter on
  the most-hit query path) and `review_brand_top_idx` (`brand`, `-rating`, `-wp_post_date`) — a
  composite that covers both the `with_stats()` aggregation and the top-review prefetch in one scan.
  This is the kind of indexing decision that separates someone who profiled a query from someone who
  guessed.

- **XSS is actually mitigated.** The template uses `{{ brand.body|sanitize_html }}` backed by an
  `nh3` allowlist filter in `catalog_extras.py`. The allowed-tags set is explicit, `rel` is excluded
  from `_ALLOWED_ATTRIBUTES` (because `nh3` manages it), and the result is `mark_safe` only after
  sanitization. This is allowlist sanitization — not `strip_tags`, not bleach — done correctly.

- **Admin is registered for all models**, including `ImportLedger`. Industry uses
  `prepopulated_fields`, Brand uses `autocomplete_fields` for both FK fields, and ReviewAdmin has a
  `date_hierarchy` on `wp_post_date`. These are not autogenerated defaults — someone thought through
  the admin UX.

### Residual gap

- **Write throughput at scale.** The importer inserts rows one at a time inside a single
  `transaction.atomic()`. For the seeded 60-review dataset that's fine; at 6 million reviews it
  becomes the bottleneck. `bulk_create`/`bulk_update` is mentioned in the README as a known
  improvement — the candidate is aware but didn't implement it.

## Pillar 2 — REST API (10 / 10)

### What lands

- **`/api/industries/` endpoint exists** and returns `name`, `slug`, and `brand_count` — unpaginated,
  because the set is small and the client needs it all at once. `IndustryListView` uses
  `annotate(brand_count=Count("brands"))` which is one SQL query, not N+1.

- **`validate_industry` uses a signal-invalidated cache** (`catalog/cache.py`). The slug set is
  loaded once, stored with a TTL, and cleared on any `Industry` save/delete signal. The TTL is
  belt-and-suspenders for multi-process deployments where signals only clear one worker — and the
  docstring says exactly that. This is production-grade awareness.

- **Public param names decouple from annotation names** (`avg_rating` → `computed_average_rating`).
  Stable API contract regardless of internal renames.

- **`nulls_last=True`** on both sort directions. Brands with no reviews don't crowd either end of a
  sort result. Most candidates miss this.

- **Stable slug tiebreak** keeps pagination deterministic across pages. Without it, a new brand
  inserted between requests could silently shuffle page boundaries.

- **`page_size` is documented** in the README: default 12, client-controllable up to max 100.

### Nothing significant to ding.

## Pillar 3 — React `<BrandList />` (9 / 10)

### What lands

- **Page is URL-synced.** `useUrlSyncedFilters` reads and writes `page` from `window.location.search`
  alongside `industry`, `sort`, and `dir`. Refresh on page 3 stays on page 3. Back-button works.
  The hook correctly resets `page` to 1 when a filter or sort changes.

- **Industry filter populates from `/api/industries/` on mount**, not from accumulated results.
  `useIndustries.js` fetches the dedicated endpoint on mount with an `AbortController`, so the
  dropdown is fully populated on a cold `?industry=banking` load. The prior `mergeSeenIndustries`
  accumulator is retained as a *fallback* in case the endpoint fails — graceful degradation without
  breaking the primary UX.

- **Explicit state machine** (`loading | success | empty | error`) rather than ad-hoc booleans.

- **Focus management** — `resultsRef` receives focus after a user-initiated filter/sort change.
  `pendingFocusRef` tracks whether the next settled state should move focus. This prevents keyboard
  users from being stranded on the control they just changed.

- **`axe` integration** in `BrandList.a11y.test.jsx`. Automated a11y testing is rare in take-home
  submissions.

- **`VisuallyHidden`** for screen-reader-only text. Correct — not `display:none`, not a CSS trick.

### Residual gaps

- **No React Suspense / streaming boundary.** With React 18's `<Suspense>` and `use()`, the custom
  `loading` state is technically a step backward from what the framework now provides natively. Not
  a blocker — the explicit state machine is readable and correct — but a senior who understands the
  React 18 roadmap would note the tradeoff.

- **`mergeSeenIndustries` has a unit test** (`mergeSeenIndustries.test.js`) but the test suite for
  the hook that invokes it (`useIndustries`) is minimal. The fallback path — industries endpoint
  fails, component degrades to result-accumulation — is not integration-tested.

## Pillar 4 — SCSS Architecture (10 / 10)

### What lands

- **7-1 pattern with `@use`** (`abstracts/`, `base/`, `layout/`, `components/`). Modern Sass
  architecture, not the legacy `@import` style.

- **Dual-variable + custom-property pattern in `_tokens.scss`** is exactly correct. SCSS variables
  for build-time use (e.g. `$bp-mobile` in media queries, which CSS custom properties cannot do),
  re-emitted as `--custom-props` for runtime theming.

- **Dark-mode token layer is implemented.** `_tokens.scss` contains a
  `@media (prefers-color-scheme: dark)` block that overrides the surface tokens (`--color-bg`,
  `--color-card`, `--color-text`, `--color-muted`, `--color-border`, `--color-star-empty`,
  `--shadow-sm`, `--shadow`). Brand hues — primary, accent, star — carry through unchanged.
  Because every component partial reads the `--color-*` custom properties, dark mode requires zero
  changes to any component file. That's the right token architecture.

- **`scss-structure.test.js`** compiles the SCSS and asserts presence of design tokens and core
  component rules. Creative and genuinely useful.

- **`$bp-mobile` comment** explicitly calls out why this is an SCSS variable and not a custom
  property — evidence the candidate understands the constraint, not just the pattern.

### Residual gap (minor)

- **No BEM namespace enforcement at the SCSS level.** Component partials use BEM at the selector
  level but `@use` namespacing is not leveraged — if two partials define `.title`, they silently
  collide in the output. Not a problem at this scale, but worth flagging as a team grows.

# Live Session — Probing Questions

These go in escalating order of difficulty. There's no single right answer to any of them —
I'm watching *how* you reason, not whether you hit a memorized answer.

---

### Q1 — Django Descriptor Protocol (Schema)

> You use `self.__dict__["computed_average_rating"] = value` in the property setter. Walk me through
> exactly *why* a plain `self.computed_average_rating = value` in the setter body would not work
> — trace it through Python's descriptor protocol. Then tell me: after I call
> `Brand.objects.with_stats().get(pk=1)` and then call `brand.save()`, what happens to the annotated
> value? Is it persisted? Is it lost? Does Django even know it exists?

*What I'm testing:* Do you actually understand why you wrote this, or did you accept AI output you
can't explain? A correct answer requires knowing that a property's `__set__` would call the setter
recursively, and that `__dict__` bypasses the descriptor lookup chain. On `save()` — Django only
writes declared model fields; the annotation lives only in `instance.__dict__` and is silently
discarded by `save()`, which is the *correct* behavior here.

---

### Q2 — Idempotency: The Ledger's Hardest Case

> A review was imported on run 1. Between runs, a Django admin went in and edited that review's
> rating from 4 to 2. Run 2 fires. Walk me through the exact code path in `_upsert_reviews()`:
> what is in `existing`, what is in `ledger_keys`, which branch executes, what SQL runs?
>
> Follow-up: Does run 2 overwrite the admin's edit?

*What I'm testing:* The "live row exists → upsert" branch. The live row *does* exist in `existing`
(keyed by `wp_post_id`). So we land in the `if live_row is not None` branch, we compare field
values from the source against the live row — and if the source says rating=4 and the admin said
rating=2, run 2 will *overwrite* the admin's edit. That's a deliberate design choice, and I want
the candidate to own it, not be surprised by it. The correct answer also notes that this is the
*only* case where "upsert wins over local edit" — which is intentional for a migration tool, but
would be a product bug in a live CMS.

---

### Q3 — nh3 Sanitization Depth

> You use `nh3.clean()` with an explicit `_ALLOWED_TAGS` set and `_ALLOWED_ATTRIBUTES` only for
> `<a>`. Tell me the specific XSS vector you're defending against. Is `nh3` doing allowlist
> sanitization or denylist sanitization, and why does that distinction matter for this use case?
>
> Follow-up: I have `<a href="javascript:alert(1)">click</a>` in the WordPress content. Does your
> sanitizer block it? What about `<a href="data:text/html,...">` as a phishing vector?

*What I'm testing:* Security depth. `nh3` (Rust/ammonia) is allowlist-based — it only permits what
you explicitly allow, unlike `strip_tags` which only strips what it knows is bad. On
`javascript:` — nh3's default `url_relative` and `url_schemes` handling blocks `javascript:` URLs
on `href`. On `data:` — worth checking whether the candidate tested this or assumed. The deeper
question is: how do you verify a sanitizer's behavior on edge cases? A strong candidate mentions
their test coverage and the nh3 changelog.

---

### Q4 — Write Throughput at Scale

> Your importer processes one row at a time inside a single `transaction.atomic()`. I have 6 million
> reviews. Walk me through what happens to *write throughput* — not read memory — as-is. How many
> SQL `INSERT` statements execute for those 6 million rows?
>
> Follow-up: You mention `bulk_create` as the fix. What is the Django-specific gotcha with
> `bulk_create`, auto-generated PKs, and SQLite vs. Postgres — and how does it affect your
> `{wp_id: pk}` FK resolution maps that the brand-phase builds before processing reviews?

*What I'm testing:* Does the candidate understand the specific failure mode, not just the buzzword?
One `INSERT` per row = 6M round-trips. On `bulk_create`: in Django < 4.1 with SQLite, `bulk_create`
does **not** return PKs on the created objects — `obj.pk` is `None` after the call. On Postgres it
works. This matters because the review phase needs the brand PK map (`{wp_post_id: brand.pk}`) to
set the FK. With `bulk_create` you'd need a second `SELECT` after the batch to rebuild the map — or
you switch to `returning=True` (Django 4.1+, Postgres only). A strong candidate identifies this
and proposes a correct solution.

---

### Q5 — React 18 and the Custom State Machine

> You implemented your own four-state loading machine (`loading | success | empty | error`). React
> 18 ships `<Suspense>` and the `use()` hook for exactly this pattern. Walk me through why you chose
> the custom state machine over the framework primitive — and what you'd need to change to migrate
> to `<Suspense>` today.

*What I'm testing:* Deliberateness vs. default. "It's what I'm comfortable with" is an honest
answer — I want to hear it. A stronger answer notes that `<Suspense>` with `use()` requires a
promise-based data source and adds RSC / streaming constraints that don't exist in a plain Vite
SPA. A senior who really understands React 18 will also note that `useBrands`'s `AbortController`
integration is harder to replicate correctly with `<Suspense>` without a caching layer (TanStack
Query, SWR) managing the promise lifecycle.

---

### Q6 — SCSS Dark Mode Strategy

> Your `_tokens.scss` defines a `@media (prefers-color-scheme: dark)` block that overrides surface
> tokens. Explain why no component partial needs to change to support dark mode. Then: a designer
> asks you to add a user-toggleable dark mode *in addition to* the OS preference — a toggle button
> that overrides `prefers-color-scheme`. What's the minimal change to your token architecture?

*What I'm testing:* Does the candidate understand what they built? The answer to the first part is
"because every component reads `--color-*` custom properties, never the `$color-*` SCSS variables
directly." The correct answer to the toggle: replace the `@media` block with a CSS class selector
(e.g. `.dark` on `<html>`) and add JavaScript to toggle the class, persisting choice to
`localStorage`. The SCSS variable declarations don't change at all — only the custom property
emission block changes. A strong candidate also notes that you'd want to honour `prefers-color-scheme`
as the *default* when no explicit preference is stored — `localStorage` absent → fall back to media
query.

### Q7 — Live Requirement (hand this to the candidate on the call, 15 minutes, AI tooling open)

> **New requirement:** Product wants `GET /api/brands/<slug>/` — a full brand detail endpoint.
>
> Response shape:
> - Everything on the card payload plus the full `body` field.
> - `reviews`: array of all reviews, each with `author_name`, `author_location`, `date`, `rating`,
>   `title`, and `body` excerpt.
> - `related_brands`: up to 3 brands in the same `industry`, excluding self, ordered by average
>   rating descending.
>
> You have 15 minutes. Use your AI tooling. I'm watching how you brief it, how you read the output,
> and what you push back on.

**What I'm watching for:**

1. **Context priming.** Does the candidate give the AI the existing `BrandCardSerializer`,
   `with_stats()`, `top_review_prefetch()`, and `Brand.objects` manager before prompting — or do they
   prompt blind and then retrofit? Blind prompting here will produce a `ModelSerializer` that breaks
   the existing serializer convention.

2. **N+1 on `related_brands`.** `related_brands` naively is `Brand.objects.filter(industry=brand.industry).exclude(pk=brand.pk)[:3]` — but those 3 brands need `with_stats()` to have a rating to order by. A naive prompt will generate this without the annotation, producing either an error or an unordered result. The correct fix is a subquery or a single `with_stats()` call on the filtered queryset.

3. **`select_related("reviewer")` on reviews.** The review serializer needs `author_name` from `Review.reviewer_name` (on the model directly — no join needed) vs. `Review.reviewer.display_name` (needs `select_related`). A candidate who hasn't read the model will generate a `select_related` on a field that might already be there — or will forget it entirely and produce an N+1.

4. **Serializer consistency.** The existing API uses plain `serializers.Serializer`, not `ModelSerializer`. A strong candidate either extends the existing pattern and defends it, or switches to `ModelSerializer` and defends *that*. What they can't do is switch without noticing.

5. **URL registration.** Does the candidate remember to wire the view into `api/urls.py`? Does the slug lookup use `get_object_or_404`? Does a nonexistent slug return 404 cleanly?
